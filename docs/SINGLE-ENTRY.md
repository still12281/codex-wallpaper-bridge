# Single wallpaper entry

Use the generated CodexEntry shortcut as the unified wallpaper entry. Repeated clicks activate the existing wallpaper client when its supervisor is alive. A normal session encountered on this entry is asked to close gracefully before the wallpaper client starts; it is never force-killed, and failed graceful shutdown stops the switch instead of opening a second profile.

New wallpaper launches no longer set `--user-data-dir`: they use the official default profile. Existing dedicated profile data is retained without copying or deleting it. This removes the intentional profile separation between ordinary and wallpaper launches; native single-instance behavior across Store updates still needs live acceptance. An already running ordinary process cannot acquire a CDP port retroactively. This change does not edit the signed application package, the Start-menu package registration or Taskband registry bytes.

The original taskbar pin is retained. The launcher, shortcut and verified owned windows use the official Codex AppUserModelID and original icon; window relaunch command, display name and icon properties are set together. Matching AppUserModelIDs does not rewrite the existing pin. A completely closed app opened through the original packaged pin still uses Windows package activation, bypassing wallpaper launch arguments and locks. A monitor can detect this afterward but cannot retrofit CDP. Warm activation and future cold startup must be reported separately; automatic wallpaper cold startup from the unchanged official pin is not claimed.

The bootstrap discovers the registered Store package after taking its lock, and resolves it again immediately before starting a new client. It scans official Codex main processes across package versions in the current Windows session, including hidden instances. Unknown process identities stop startup. Main, direct-fallback and recovery launches all check for existing roots; CDP reuse also rejects an extra root. Only the same verified owned process can be gracefully closed, and a launch forwarded to an existing root is not claimed as a newly owned process. These checks prevent the wallpaper launcher from deliberately creating another client, but cannot provide an operating-system-wide lock against an independent official activation racing it.

Run the isolated policy regression with PowerShell 7: `pwsh -NoProfile -File test/launch-policy.ps1`. It verifies old/new version detection, CDP-owner exceptions, hidden-main blocking, unknown-identity rejection and absence of a custom profile argument. It does not restart a real Codex client or prove native singleton behavior.
