# Single wallpaper entry

Use the generated CodexEntry shortcut as the unified wallpaper entry. Entry checks run only when clicked; it waits for its one-shot PowerShell bootstrap and reports failure before exiting. Repeated clicks validate the existing client and wallpaper bridge before activating that window. No supervisor is built or started by this entry. An existing ordinary session is preserved: the entry explains that the user must exit it normally before reopening through the wallpaper shortcut. It does not automatically close or restart that session.

The wallpaper bridge stays connected while import, switching, detached-window support and optional system media are available. It retains page synchronization and media timers; it does not scan OS processes or restart Codex. A browser WebSocket disconnect triggers cleanup and bridge exit. There is no external five-second process supervisor or automatic restart loop. Existing installations should disable the legacy `CodexWallpaperBridge-Supervisor` scheduled task. A failed bridge can be reconnected on the next explicit entry click.

Launcher and shortcut icons use the installed Windows manifest's original unplated PNG assets, wrapped in an ICO directory with their payloads unchanged. The Electron `app/resources/icon-chatgpt.ico` has a different glossy design and must not be used for Windows-native consistency. The canonical icon is `icons/Codex-Native.ico`; `Codex.ico` remains a matching compatibility copy. No pixels are redrawn, resized or bundled with the source.

Icon preparation also checks the real fixed shortcuts under `User Pinned`, including `ImplicitAppShortcuts`. Only shortcuts targeting this exact entry have their icon reference refreshed; names, targets, arguments and working directories are retained. A per-item Shell update notification flushes the old path's cached image. Relaunch-property readback alone does not prove the currently displayed taskbar icon; visual readback is a separate check.

The build records the PowerShell executable actually running it and the resolved Node executable in `launcher-runtime.json` beside the generated entry. Entry resolution checks explicit environment overrides, that file, PATH and standard install locations. This supports portable PowerShell and Explorer environments whose PATH was captured before runtime setup. The file is local installation state and must not be committed; rerun the build if a runtime moves.

New wallpaper launches no longer set `--user-data-dir`: they use the official default profile. Existing dedicated profile data is retained without copying or deleting it. This removes the intentional profile separation between ordinary and wallpaper launches; native single-instance behavior across Store updates still needs live acceptance. An already running ordinary process cannot acquire a CDP port retroactively. This change does not edit the signed application package, the Start-menu package registration or Taskband registry bytes.

The launcher, shortcut and verified owned windows use the independent desktop AppUserModelID `CodexWallpaperBridge.Codex` and the original official icon. Sharing the Store package ID previously allowed the fixed entry to remain package activation and bypass wallpaper launch arguments. Window relaunch command, display name and icon properties are set together for every visible top-level window of the verified process. This does not rewrite an existing pin. The user must unpin the original packaged entry and pin the generated `Codex.lnk`; copying it into a directory is not proof of taskbar registration. No Taskband registry rewrite, screen automation or silent pinning is part of the build. Cold launch and single-icon grouping remain native acceptance steps.

Bootstrap success requires a fresh matching browser/process result and a ready installed target. Native capture additionally requires a produced frame; paused capture is valid after that first frame. A stale bridge from another browser identity is never reused. Inspection writes `entry-inspect-status.json` instead of overwriting the active launch identity. Startup failures return a nonzero result and their reason is displayed by the entry; they cannot silently appear to be a successful wallpaper launch.

The bootstrap discovers the registered Store package after taking its lock, and resolves it again immediately before starting a new client. It scans official Codex main processes across package versions in the current Windows session, including hidden instances. Unknown process identities stop startup. Main, direct-fallback and recovery launches all check for existing roots; CDP reuse also rejects an extra root. Only the same verified owned process can be gracefully closed, and a launch forwarded to an existing root is not claimed as a newly owned process. These checks prevent the wallpaper launcher from deliberately creating another client, but cannot provide an operating-system-wide lock against an independent official activation racing it.

Run the isolated policy regression with PowerShell 7: `pwsh -NoProfile -File test/launch-policy.ps1`. It verifies old/new version detection, CDP-owner exceptions, hidden-main blocking, unknown-identity rejection and absence of a custom profile argument. It does not restart a real Codex client or prove native singleton behavior.

Run `node test/lifetime-integration.mjs` to verify that a bridge attached to an isolated headless browser exits with status zero when that browser closes. It does not interact with the current Codex, taskbar or user browser profile.

After building into an isolated data directory, run `pwsh -NoProfile -File test/launcher-runtime.ps1 -BuildDirectory <absolute-build-directory>`. This invokes the actual entry with empty PATH and cleared runtime overrides, executes bootstrap inspection only, and checks that existing client identities remain unchanged. It verifies dependency resolution without closing or starting a user client; a real wallpaper cold launch is a separate acceptance step.

## Existing-client activation, 2026-10-26

An already verified browser/root is reactivated through the official package activation API, then the exact main CDP page is brought forward. Detached pages cannot substitute for the main page. The deployed app/src host path is recognized as the existing host. Real activation retained the same client/browser/main target and took approximately 1.25 seconds in the latest bounded check. Closing the real main window and cold-start acceptance remain pending; the current Codex was never force-closed or restarted.

The unused supervisor source and its deployed executables were retired; the exact disabled legacy scheduled task was removed. No new resident supervisor or monitoring service was added.
