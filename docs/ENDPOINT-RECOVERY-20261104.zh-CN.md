# 默认端口残留与安全恢复

## 原因

本机出现 `127.0.0.1:9335` 仍为 LISTEN、记录旧 Codex PID，但 CIM 与原生进程查询均无该进程、HTTP 接口不响应的状态。入口此前固定使用 9335，因此即使已正常退出客户端也会停止启动。端口残留的系统层原因尚未定位，不能归咎于用户退出方式；启动器应能保留占用者并避开失效端口。

## 修复

- 优先重新验证保存端点及默认端口。没有可复用连接时，从 9335–9354 选择空闲端口；不关闭占用者，不绑定公网地址。
- 保存的 `cdp-endpoint.json` 与 `runtime-status.json` 只提供端口提示。每次均验证唯一监听 owner、当前 Windows session、官方登记的主程序路径、进程创建身份和实际 CDP 浏览器；损坏记录、其它会话、辅助进程及 PID 变化均拒绝复用。
- CIM 的创建时间只有微秒精度。与原生创建时间作精度容差核对后，记录原生 100ns 时间，避免把同一进程误判为已替换。
- 启动前重查主实例及端口，端口被抢占时重新选择；普通主实例仍存在时不另开第二份。现有协议重定向回退也重查端口，更新事件仍不新增关闭或重试。
- 验证连接后原子保存端点提示；保存失败只记警告，不触发关闭健康客户端。壁纸宿主、任务栏对齐与更新恢复使用同一实际端口。
- 入口互斥/事件名称保持稳定，不因不同端口绕过单入口保护。`npm start` 仍是手动开发诊断用的 9335 默认命令，普通使用通过一体入口。

## 已验证与剩余验收

`test/cdp-endpoint.ps1` 覆盖端口占用、空闲后备、保存端点重新验证、非法/损坏记录、全部占用、会话/主进程/创建身份及精度核对。`test/startup-shutdown.ps1` 执行实际 bootstrap 并隔离包/进程/激活接口，验证 9335 残留时只发一次 9336 调试启动、9336 临时被占时改用 9337，以及普通实例仍运行时不启动。启动策略、健康记录、更新 no-close 回归通过；没有操作真实占用者。

本机入口已指向修改后的源码。当前普通客户端没有开放 CDP，需要正常退出后由一次性恢复入口启动；实际首帧及端点保存/复用仍需实机验证。相关状态以运行日志与用户可见结果为准，不把隔离测试当作已恢复。私人设置、占用快照和恢复日志保留在仓库外。
