## 容量问题

截图32MiB来自旧mediaLimits：1280及以下、30FPS及以下媒体副本32MiB，其余128MiB；播放端又限制为最多128MiB。这是本项目整文件ArrayBuffer/Blob/CDP加载的保守策略，不是硬件、Wallpaper Engine或场景包通用限制。“按原规格尝试”不会解除保护；提高画质以改变预算也不是合理的大文件方案。

用户随后明确指出常见几百MB/几GB壁纸。后续优先改变整文件加载路径：视频采用文件支持的Blob/流式读取，避免整体Base64、完整ArrayBuffer与重复内存副本；大场景包与转码资源预算仍须分别处理，不能只抬数字就宣称支持几GB。

## DSH 到底怎样做网页

已读本机固定源码：dsh-wallpaper-engine `3b0103bc1d5431840208966ce67155f392c4095c`，webwallgl `197abe54266c31d346cebc314e49a26b70c960cc`，均与UPSTREAM-SOURCES记录一致。

1. DSH插件在应用中使用同源、无sandbox的可信renderer iframe；第三方网页再进入allow-scripts的opaque iframe。源码：DSH `src/live-layer-pointer.js:404`、`lib/routes/scene-serve.js:80`、`src/live-layer.js:177`。
2. DSH独立的127.0.0.1随机端口媒体服务提供完整HTML/资源，注入WE shim、属性seed和site-root，并做字面路径及realpath围栏。`lib/media-origin.js:140`、`lib/serve.js:239`、`lib/serve.js:464`。这解决其桌面宿主能力头栅栏，不证明Codex官方页面允许同样的源。
3. WebWallGL Web入口同源时直接导航，跨源时fetch→base/shim改写→Blob iframe。`renderer/src/web.ts:1381`及`:1411`。我们现有Scene字节broker没有提供这套浏览器资源目录。

所以“现有Codex GPU iframe通道没打通”不能推成“网页做不到”。此前“通用Web优先WE采集”的结论只是在当前实现中选后备，不是对所有可行方案的否定。

可选新路线为：**项目自有Electron/Chromium窗口 → DSH/WebWallGL网页装配 → 现有WGC/JPEG → Codex canvas**。固定webwallgl已有 `desktop/main.mjs:71` 的本地服务与 `:91` 的sandbox/contextIsolation窗口骨架，现有capture-scene按自有窗口HWND采集，不绑定WE引擎。但它不是DSH Desktop主进程，权限处理不能原样全放行；当前也没有现成通用Web离屏输出。作者仍须opaque sandbox，可信wrapper单独持有preload，按选中项启动、切走退出。

这条路线不需要改Codex CSP，不需要常驻监控，也可以保持一体入口。真正未验证的是屏外连续出帧、首载及总内存、音频/属性/暂停、输入转发、多窗口与退出清理；当前不能称已实现。完整DSH Desktop主进程源码不在本机研究目录，不把插件注释冒充主进程安全验证。
